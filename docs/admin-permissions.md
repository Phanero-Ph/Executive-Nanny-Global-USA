# Administrator invitations and permissions

Open **Team & settings → Administrator accounts → Invite administrator**. Enter the person's name and email, choose Recruitment Manager, Finance, Support, Training Manager, Custom, or (for Super Admins) Super Admin. Expand **Customize permissions** to adjust access, then choose **Send invitation**. Required view permissions are included automatically.

The invitation is queued atomically in the existing email outbox. After the transaction commits, the application attempts delivery immediately; failed delivery remains pending for the existing retry worker. The recipient opens the link within 48 hours, chooses and confirms a password of 12–128 characters, and verifies ownership of the invited email by completing this step. Acceptance activates the account; the recipient then signs in normally. The inviter never chooses or sees their password. Existing family/nanny accounts cannot be converted through this interface.

Expand a team member to update permissions, suspend/restore access, or resend/revoke an unaccepted invitation. Resending replaces all previous invitation links. Links are stored as SHA-256 hashes, expire after 48 hours and can be accepted only once. No raw token is returned by the management API or included in audit records. The private email outbox necessarily contains the acceptance URL until delivery; existing mail delivery clears delivered bodies.

Migration 0018 adds `admin_access`, `admin_invitations`, and a singleton administrative lock. It gives pre-existing administrator accounts Super Admin access to preserve their previous unrestricted capabilities. Newly created role=admin rows without an explicit active access record have no administrator access. Public signup still cannot grant the admin role. The local `admin:create` provisioning helper explicitly creates a Super Admin and refuses existing accounts.

Permissions are checked from the database on server pages, mutation APIs, exports and private document/file routes. Staff have separate family-chat and nanny-chat permissions. Conversation lists, contact search and notifications exclude areas they cannot access. Admin dashboard queries and embedded membership data are scoped to assigned areas. Buttons and sidebar items follow the same grants. Open workspaces refresh grants every 15 seconds and on focus; server checks apply immediately to subsequent requests. Permission changes do not require signing out. Suspension increments the session version, invalidating previous sessions; login also refuses invited/suspended accounts.

Only staff with `admins.manage` can manage accounts. Non-super administrators can grant only permissions they already hold and cannot manage a target whose permissions exceed their own. Only Super Admins can assign or modify Super Admin access. A database lock serializes management and invitation acceptance, including concurrent suspension/demotion; at least one active Super Admin must remain. An administrator cannot suspend their own account. Access changes are recorded with actor, time, target and before/after grants. Non-super team managers see only administrator access/invitation audit events; Super Admins can see broader administrative activity.

Run `npm run test:admin-permissions` for isolated integration tests. They create and remove a generated local scratch database using the local maintenance connection, deliver no email and do not modify application accounts. Set `ADMIN_TEST_DATABASE_URL` privately if the maintenance connection differs from the local root connection. The scratch database uses utf8mb4_unicode_ci to match the schema. `npm run test:chat-controls` verifies the existing independent group switches. `node scripts/test-chat-controls-ui.mjs` checks rendered visibility for restricted administrators. `node scripts/check-admin-settings-ui.mjs` checks desktop/mobile controls with a disposable local Super Admin without sending invitations.
