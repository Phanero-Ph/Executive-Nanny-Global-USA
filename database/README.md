# Next.js + MySQL setup

The website and API run in Next.js. MySQL stores the data; phpMyAdmin is its administration interface, not the database server.

## Local setup
1. Create an empty MySQL 8+ or MariaDB 10.6+ database and an application user with access to that database.
2. Copy `.env.example` to `.env`, fill in DATABASE_URL and a random SESSION_SECRET. URL-encode reserved characters in credentials. Never share or commit the populated file.
3. Install dependencies with `npm install`.
4. Initialize an empty database using either `npm run db:migrate` OR phpMyAdmin: select your database, open Import, and import `database/schema.sql`. Do not apply both to the same database. CLI migrations are preferred for future schema changes; the SQL import is the initial cPanel setup option.
5. Run `npm run db:check`, then `npm run dev`.

Existing PostgreSQL data is not automatically converted. No existing database has been modified by this source-code change. If there is data to preserve, export and migrate it separately before switching connections.

## Namecheap shared hosting
Create the database and user through cPanel MySQL Databases, assign the user to the database, and use the complete cPanel-prefixed names in DATABASE_URL. Use the host provided by Namecheap (often localhost). Import schema.sql through phpMyAdmin if not using CLI migrations.

Configure a supported Node.js runtime through Setup Node.js App. This app needs a running Next.js server; uploading only public files will not provide working authentication or forms. Build before running the production server. The exact Node application startup integration must be checked on your hosting account before deployment.

Set DATABASE_URL, SESSION_SECRET and NODE_ENV=production in the hosting application's environment. Keep credentials private and enable HTTPS. Application files and `.data/nanny-uploads` must be in the private application directory, outside public_html. Back up the database and private uploads together. The database pool is capped at five connections per application process.

## Verification
Run `npm run typecheck`, `npm run lint`, and `npm run db:check`. With the database connected, verify family and nanny registration, duplicate-email handling, login/logout, dashboard ownership, contact submissions, and application uploads using a test database.

Account creation and its care request/application are saved in one transaction. Passwords remain hashed. Nanny application's structured answers use a LONGTEXT column to accommodate the complete application. IDs are generated by the application, including when importing the SQL schema through phpMyAdmin.

## Configured local XAMPP environment

The application database is executive_nanny on 127.0.0.1:3306. A dedicated egn_app user has access only to that database. Generated credentials and SESSION_SECRET are stored privately in .env. phpMyAdmin is served natively by PHP at http://127.0.0.1:8081/.

Start Apache and MySQL from XAMPP Control Panel, then run npm run db:check and npm run dev. Schema migrations have been applied through Drizzle; do not also import schema.sql into this database. Docker is not used. The installed MariaDB 10.4 server is for local development; use the hosting provider's maintained database version for production.

Use the application credentials from .env if phpMyAdmin requests a database login. Do not share or commit that file.

The native phpMyAdmin server is running separately from Apache. After restarting your computer, start MySQL in XAMPP Control Panel, run npm run db:admin in one terminal, and npm run dev in another. Run npm run test:local to repeat the local end-to-end checks; the script cleans up its own temporary accounts and files.

## Administration
The admin dashboard is at `/dashboard/admin`. Public registration cannot create admin accounts. Administrator access is checked against the database on every protected request. Admin status updates are transactional and include immutable review history with reviewer identity and internal notes. Internal notes are not shown in family or nanny dashboards. Document access is restricted to the owning nanny or an administrator.

`npm run admin:create` provisions a LOCAL administrator with a random password, stored in the ignored `.data/admin-credentials.txt`. The helper refuses to promote or overwrite an existing account. Run it only after authorization for the administrator identity and access scope. Production admin provisioning requires a separate explicit setup.

Review status changes do not mark fees paid or activate subscriptions. Those financial workflows will be implemented separately.

## Nanny matching and placements
Open a family request in the admin dashboard to shortlist approved, active nanny applications. Use the matching panel to schedule interviews, record a placement start date, or close a match. Interview times are entered and displayed in Africa/Lagos time (WAT).

Only one active placement is allowed per family request and per nanny account. Placement updates synchronize the family request and nanny application, close competing matches for that request, and record review history. Close an existing placement through the matching panel to release the request and nanny for matching again. General review status edits cannot create or remove a placement.

Families and nannies see only their own matches and the explicitly shared note. Private application answers, documents, and internal review notes remain restricted. Match updates queue notifications using the configured email mode; local preview mode does not send real email.

## Email and account recovery
The sender is egnmails@gmail.com. Gmail is configured with smtp.gmail.com:587 and STARTTLS. Add a Google App Password to SMTP_PASS in the private .env file, run npm run mail:check (authenticates without sending a message), and change EMAIL_MODE from preview to smtp when ready. Production also needs a public HTTPS APP_URL. Never put the SMTP password in chat, source code, or public files.

Local preview mode writes emails to the ignored .data/mail-preview directory. These files contain private verification/reset links. Do not publish or share them. Preview mode is disabled in production. Confirmation emails are generated for family requests and nanny applications. Verification emails are generated for new accounts; users can resend from their profile. Admin status changes generate a status email, excluding internal notes. Note-only reviews do not send emails.

Email jobs survive delivery failures. Run npm run mail:retry to process pending messages (up to 50 per run and five attempts per message). On hosting, configure cPanel cron to execute scripts/process-mail.mjs from the application directory with the application environment loaded. Monitor pending jobs with five attempts; fix SMTP and deliberately reset attempts for affected jobs before retrying. SMTP delivery is at-least-once: a connection failure after server acceptance can cause a duplicate email on retry.

Password-reset links expire after 30 minutes; verification links expire after 24 hours. Tokens are random, hashed in the account-token table, and single-use. Reset requests use a generic response and database-backed throttling. A successful reset invalidates old sessions and outstanding reset links. Reset/verification links are consumed only after a POST, not by viewing the page. Delivered email payloads are cleared from the queue; local preview copies remain private on disk until cleaned up. Pending email jobs necessarily retain their message body until delivered.

Run npm run test:recovery and npm run test:local in preview mode against the local test database. No real email is sent by these tests. Local SMTP delivery remains unverified until the Gmail App Password is supplied.

## Family memberships and offline payments
Open any linked family request in the admin dashboard to manage the account's monthly membership. Plans use the published Basic $59, Standard $89, Deluxe $129 and Premium $200 USD rates. Each cycle runs from the start date until the same date next month (exclusive), with month-end dates clamped. Overlapping uncancelled cycles are rejected. Create the next cycle explicitly to renew; this does not charge the family automatically.

Record actual received payments with a unique transaction reference. Partial payments are supported; only fully paid cycles are active during their dates. Receipts cannot be deleted or edited. Void an incorrect receipt with an internal reason, then record its replacement with a new reference. Voiding does not initiate a refund. Resolve recorded payments before cancelling an unpaid cycle. Memberships do not change search-fee, placement, caregiver-subscription or booking-usage records.

Payment confirmations and corrections are saved transactionally to the durable email queue. Run `npm run membership:reminders` daily, followed by `npm run mail:retry`. On hosting, schedule both commands with cPanel cron using the application's environment. Renewal reminders are queued once per fully paid cycle within seven days of expiry, unless a following cycle already exists. Local preview mode creates private previews; Gmail sending still requires SMTP_PASS and EMAIL_MODE=smtp.

## Stripe recurring family memberships
The family dashboard offers Stripe-hosted monthly Checkout for Basic ($59), Standard ($89), Deluxe ($129), and Premium ($200), plus a customer billing portal. Caregiver subscriptions, search fees, placement fees and booking consumption remain separate. Published membership buttons on Services and Pricing lead to the family dashboard. Families sign in before checkout.

1. Add a Stripe **test** secret key as `STRIPE_SECRET_KEY` in the private `.env` file. Do not commit or share it.
2. Run `npm run stripe:setup`. This creates/reuses four monthly USD prices and a dedicated portal configuration, saving their IDs privately in `.env`. The portal permits payment-method changes, invoices and cancellation at period end; plan changes and prorations are disabled. Complete the Stripe business profile as required by your account.
3. Forward snapshot events locally with `stripe listen --events checkout.session.completed,checkout.session.expired,customer.subscription.created,customer.subscription.updated,customer.subscription.deleted,invoice.paid,invoice.payment_failed,charge.refunded --forward-to localhost:3000/api/billing/webhook`. Put the listener's signing secret in `STRIPE_WEBHOOK_SECRET`, then restart the dev server.
4. With a test family, complete each plan's Checkout using Stripe test payment details. Confirm that only a paid invoice activates the membership; visiting the success URL alone does not. Exercise failed renewal, portal cancellation and refunds in the Stripe test dashboard.
5. For production, configure separate live prices/portal IDs and a public HTTPS snapshot webhook at `/api/billing/webhook`, using API version `2026-09-30.endive` (the installed SDK version). Supply the live endpoint signing secret and live secret key privately, with `STRIPE_ALLOW_LIVE=true`. Keep test and live databases separate. The setup helper intentionally provisions only test resources.

The webhook verifies the raw request signature and event mode. It reads current Stripe subscription/invoice data, deduplicates event and invoice IDs, and commits receipts and notification jobs together. Failed processing returns a retryable response. Monitor failed deliveries in Stripe and resend after resolving configuration or database errors. No card details are stored by the application. The portal always uses the signed-in account's stored customer ID. Offline membership edits cannot alter Stripe receipts, and existing manual memberships must be resolved before starting Stripe billing.

Stripe billing periods retain exact timestamps. Paid cycles expire at the actual period end; end-of-period cancellation preserves access until then. Failed renewals do not create paid cycles. Refund events update refunded totals without deleting original receipts; an underpaid/refunded cycle no longer counts as active. Manual renewal reminders exclude Stripe cycles; configure Stripe's customer email settings for upcoming renewals and failed payments. Application confirmations use the durable mail queue (`npm run mail:retry`).

`npm run test:stripe` runs isolated SDK fixtures against the local database, including genuine SDK signature verification, checkout reuse, ownership, duplicate events, stale event order, failed payments, refunds and cancellation. It makes no Stripe requests and cleans temporary records. Actual Stripe test-mode checkout still requires account keys and the local webhook listener. Test and live credentials must never be mixed in the same database.

Stripe references: [subscription integration](https://docs.stripe.com/billing/subscriptions/build-subscriptions), [webhook verification and retries](https://docs.stripe.com/webhooks), [customer portal sessions](https://docs.stripe.com/api/customer_portal/sessions/create).

On Windows environments that deny Next.js child-process workers, set `EGN_BUILD_THREADS=true` for the build command to use two worker threads. Type checking remains enabled. The default build configuration is unchanged when this variable is absent.

## Babysitting bookings
Families use `/dashboard/family/book` to request care, with start/end times, town, care address and care needs. The entire booking (30 minutes to 24 hours) must be inside a currently active, fully paid membership period. All booking times are explicitly entered/displayed in Africa/Lagos (WAT, UTC+1), and stored in UTC. Membership covers booking access; caregiver wages remain separate.

Basic allows 3 bookings, Standard 5, Deluxe 8, and Premium unlimited per paid membership cycle. Requests reserve allowance immediately; pending, accepted, confirmed and completed bookings count. Cancellation before care starts releases allowance. Only admins can cancel after care starts; those cancellations still count. Duplicate submissions reuse their request key, and account locks make quota checks safe under concurrent requests. Overlapping family requests are rejected.

Admins open `/dashboard/admin/bookings` to filter bookings and invite approved, active caregivers. Assigned caregivers see care needs and town, then accept or decline in their dashboard. Acceptance unlocks the full care address and family phone; an admin then confirms the booking. A decline returns the request to the admin queue for reassignment. Reassigned caregivers retain only minimal invitation history. The backend rejects overlapping caregiver assignments and caregivers with active placements, stale saves, unapproved caregivers, and confirmations after the scheduled start. Admins can mark confirmed care completed only once the care period has ended.

Only the owning family, current assigned caregiver, and admins can view relevant booking details. Internal history/notes remain admin-only. Transactional email jobs notify the family, affected caregivers and administrators without including care needs, addresses, contact numbers or private notes. Use the existing `npm run mail:retry` delivery job; local preview mode does not send real messages.

Run `npm run test:bookings` against the local development database with EMAIL_MODE=preview. It exercises real API sessions, membership eligibility, all plan limits, concurrent requests, invitation responses, timing conflicts, cross-account privacy, internal notes, cancellations and completion. Temporary users, bookings and queued test notifications are cleaned up. Stripe activation is not required for manual membership bookings.

## Training Academy
Admins manage courses at `/dashboard/admin/training`. Create a draft with a title, summary, instructor and duration, then add ordered lessons with text and/or private PDF materials (up to 10 MB each, 100 lessons per course). At least one lesson is required before publishing. Published curricula are immutable; create a new course version to revise materials. Archive a course to stop new enrollments while preserving access and review for existing learners. No course content or certificates are automatically fabricated or seeded.

Registered caregiver accounts enroll at `/dashboard/nanny/training`, complete lessons, and submit a completion reflection. All lessons must be marked complete before requesting review. Instructors inspect progress, reflection and any practical assessment before approving completion; marking lessons alone never issues a certificate. Admins may return a submission with feedback visible to the caregiver. Review notes remain private. This module does not charge training fees or activate caregiver subscriptions; published courses are available to registered caregivers.

Approved completion creates a certificate with immutable snapshots of the course title, trainee name, approving administrator and issuance date. The caregiver or an admin can open its private certificate page and use Print / save as PDF. Certificates and materials are not publicly accessible. Approved courses appear on caregiver profiles and recruiter-managed shortlists; families see course names, without private certificate links or reflections. Admins can revoke a certificate with an internal reason, removing it from profiles and disabling its printable page. Reissue creates a new certificate while preserving the revoked record and history.

PDF materials are stored in the ignored `.data/training-materials` directory, outside public files. Back up this directory with the database and other private uploads. Only admins and enrolled caregivers can download materials. Email review/result notifications use the existing durable queue and exclude lesson text, reflections and internal notes. Use `npm run mail:retry` as already configured; local preview mode does not send real email.

Run `npm run test:training` in local preview mode to verify draft/publication rules, material permissions, curriculum locking, progress integrity, instructor feedback, concurrent approvals, certificate ownership/snapshots, revocation/reissue, profile visibility and archive behavior. It creates fictional courses and temporary accounts and removes its PDFs, certificates, records and notifications after testing.


### Caregiver credentials
Caregivers upload private PDFs at `/dashboard/nanny/credentials`. Admins review at `/dashboard/admin/credentials`, verify the issuer, record internal evidence, and set an expiry or next review date. CPR, First Aid and background check documents are required. Existing caregivers need to submit these before new assignments; prior approvals are not treated as document verification.

Expiry is inclusive through the recorded UTC calendar date. Bookings require all three verified credentials through the end of care; placements require them through the later of today or the placement start. Replacement uploads immediately reset verification. Existing bookings/placements are retained for manual review, not automatically cancelled. Credential files and review notes are private to caregivers/admins (notes admin only). Prior replacement files are retained privately for audit retention; include `.data/credentials` in protected backups.

Run `npm run credentials:reminders` daily, then `npm run mail:retry` every five minutes using the documented Node cron approach. The reminder job queues caregiver/admin alerts once per credential revision when expiry is within 30 days or already passed. It does not install a scheduler. Email remains in preview mode until Gmail SMTP is configured.


### Private care messaging
Open `/dashboard/messages` from each account dashboard. Conversations start from accepted/confirmed bookings or shortlisted/interview/placed nanny matches. Only the linked family, currently linked caregiver and administrators can access them. Closed matches and completed/cancelled bookings retain read-only history. Reassigned booking caregivers lose access to the old conversation; the new caregiver receives a separate conversation. Families/admins retain the old history. Messages are plain text (maximum 2,000 characters); document uploads and public messaging are not supported.

The inbox shows the 100 most recently updated conversations, with unread counts. Open conversations refresh every 15 seconds while the page is visible; there is no websocket service requirement. Older messages load in batches of 50. Read cursors advance only through an authenticated POST and never move backwards. Sends use a unique request key to make retries safe, and serialize per conversation to preserve ordering; each sender may send up to 20 messages per minute per conversation.

Email notifications contain only a private dashboard link, not message contents or care details. Notifications use the existing durable mail queue and `npm run mail:retry` scheduler; Gmail SMTP is still required for real delivery. Administrators can read/reply through the shared inbox, and their messages are labelled Agency team. Each administrator has a separate read cursor. Conversations are stored in MySQL and should be included in protected database backups.

Run `npm run test:messaging` against the local server on port 3001 with EMAIL_MODE=preview. The test uses temporary accounts/records and cleans them up without sending real email or making payments.


### Dashboard workspace
Family, caregiver and admin dashboards use a shared authenticated workspace with a sidebar, mobile navigation, role-specific overview metrics and separate task views. Public website navigation and the footer remain on public pages; private pages use the workspace header and compact footer. Certificates keep their standalone print layout.

Family task links use `/dashboard/family?view=requests`, `bookings`, `matches`, `membership`, or `profile`. Caregiver task links use `/dashboard/nanny?view=application`, `bookings`, `matches`, or `profile`. Credential reviews, training, admin bookings and messages keep their existing routes. Existing application, booking, billing and document permissions are unchanged.

Local integration checks default to port 3001. For a development server on port 3000, set `$env:EGN_TEST_URL='http://localhost:3000'` before running `npm run test:local`, `npm run test:bookings` or `npm run test:training`.

Development builds use `.next-development`; production builds use `.next`. These separate output directories prevent a production build from invalidating a running development server. The standard local app URL is `http://localhost:3000`; `npm run dev` and APP_URL use this port.

Gmail SMTP was verified with implicit TLS on port 465; port 587 timed out on this connection. The private local configuration now uses SMTP_PORT=465 and EMAIL_MODE=smtp. `npm run mail:check` verifies authentication without sending email. Local fixture tests require preview mode in both the running application and test process; restore SMTP mode afterward.


## Placement flows (current)

Apply migrations with `npm run db:migrate` before running the updated app. Migration 0011 adds nanny/caregiver categories, membership cycle and submission idempotency tracking, and the caregiver fee ledger. Existing requests retain their IDs and default to nanny placement; historic requests without a cycle do not consume newly tracked submission allowances.

Nanny placement requires a fully paid, current family membership. Each request consumes one submission in its paid billing cycle: Basic 3, Standard 5, Deluxe 8, Premium unlimited. Cancelled requests still consume their submission; retries with the same submission key do not. User-row locking serializes simultaneous submissions. A subscription must remain valid while admin progresses the search or placement. Search and placement company fees are included. The limits no longer apply to care bookings; existing booking eligibility and schedule/credential checks remain.

A caregiver request needs no subscription. Stripe Checkout collects $50 USD search payment and a separate $50 USD placement payment for each request. Admin cannot search, shortlist, or interview until the search fee is confirmed. After agency candidate selection, admin sets the request status to `placement_fee_due`; the family can then pay the second fee from Care requests. Match placement requires both confirmed fees and current caregiver credentials. Wages are separate. All request status APIs enforce these rules; changing a status cannot forge payment.

Fee Checkout uses server-defined amounts and persistent idempotency keys, reuses open sessions, verifies Stripe payment intent and session metadata, and records unique request/kind fees. Redirects never mark a fee as paid. Webhooks and scheduled event recovery share the same transactional handler. Partial/full refunds remove payment eligibility and display an agency-contact message; they never automatically charge again or undo an existing work placement. Admin should review placements after refunds.

No new Stripe environment variables or Dashboard prices are required: one-time Checkout fees are defined server-side. Existing checkout completed/expired and charge refunded event subscriptions also cover caregiver fees. The deprecated anonymous `/api/family-requests` lead endpoint returns 410; the home CTA and registration form route families through the authenticated placement flow.

`EMAIL_MODE=preview npm run test:stripe` (PowerShell: `$env:EMAIL_MODE='preview'; npm run test:stripe`) tests both placement flows with mocked Stripe and temporary MySQL fixtures; no network payments or email delivery occur.


### Caregiver request entry point

`/dashboard/family/book` now submits a caregiver placement request to `/api/find-nanny` with `careCategory=caregiver`. It collects contact information, preferred start date, flexible/long-term duration and schedule, location, recipient and requirements. It has no membership check, booking end time, or 30-minute/24-hour duration validation. After saving, the existing $50 search fee checkout is available immediately. The caregiver dashboard section is `?view=caregiver`, with per-request fee controls; fee redirects and notifications return there. Nanny requests remain in `?view=requests`. The existing `care_bookings` records and API are retained for previously scheduled assignments and are not used to submit new caregiver placements.


### Admin release after payment

Unpaid caregiver placement requests remain visible only to their family. The admin queue, counts, detail page and review/matching endpoints require a confirmed $50 search-payment ledger entry (`caregiver_fees.paid_at`). Opening Checkout, returning from it, or manually editing the request status cannot publish a request. Both live webhooks and recovery release it by committing the verified payment. Nanny submissions already require a paid subscription. Once a caregiver request has reached admin following a confirmed payment, it stays visible if refunded so the team can resolve it; payment/refund gates still block progression. No caregiver submission email is sent at the unpaid stage; the verified-payment confirmation remains queued by the webhook handler.


### Admin matching workspace

Open `/dashboard/admin/matching` or choose **Matching & placements** in the admin navigation. Select a payment-confirmed family request, then choose an approved (`active`) application and add it to the shortlist. Update the match to schedule an interview or confirm placement. Fee, subscription, credential and conflicting-assignment checks remain enforced by the existing matching API. Dashboard family rows and the request detail page also link directly into this workspace. It does not automatically approve candidates or create matches.


### Agency-led placements

Family-to-candidate interviews are no longer part of placement matching. Shortlisted candidates can move directly to placed, subject to existing payment, subscription, credential and assignment checks. For caregiver requests, after selecting a shortlisted candidate the admin sets Candidate selected / placement fee due; placement still requires the final confirmed $50 payment. New interview match transitions are rejected. Migration 0012 moves existing match/request interview states back to shortlist and increments match revisions. Historical interview dates and audit history are retained in the database but no interview scheduling control is shown. Agency recruiting/screening statuses for worker applications are independent and remain available.
